Target architecture

Sensors
  -> time/quality validation

The dashboard must remain a consumer of the brain’s public output. It must not calculate threat, infer identity, or make control decisions.

Phase 0 — Define the operational envelope

Before tuning algorithms, record explicit requirements for:

• Maximum target speed, acceleration, turn rate, climb/descent rate, and jerk.
• Sensor update rate, latency, timestamp error, dropout duration, and expected false detections.
• Minimum detection range and available warning time.
• Number of simultaneous targets and closely spaced targets.
• Spoofed identity behavior, RF loss, GNSS denial, clutter, birds, friendly aircraft, and crossing tracks.
• Clock source, coordinate frame, altitude reference, and maximum allowed end-to-end latency.

“Fastest drone” must become a measurable envelope. A tracker that performs well at 30 m/s may fail badly at 100 m/s if the scan period, gate, coast time, or process latency is unchanged.

Phase 1 — Make tracking robust before adding live input

Use two or more explicit models:

• Constant velocity for stable cruise.
• Coordinated turn or acceleration/Singer model for manoeuvres.
• IMM mixing with model probabilities, but expose the probability as diagnostic metadata only—not as an “evasive” classification.

Required tracker behavior:

• Association cost combining Mahalanobis distance, velocity consistency, and authenticated sensor/signature evidence.
• Gating sized for the stated speed and scan interval, not a fixed simulator value.
• Track confirmation and deletion based on time and evidence, not only scan count.
• Adaptive coast time based on target speed, uncertainty growth, and sensor quality.
• Stable track IDs through short dropouts and crossings.
• Out-of-sequence measurement handling or an explicit rejection/audit path.
• Positive-semidefinite covariance checks and numerical fault handling.
• Track freshness, age, missed scans, sensor support, and quality state in the internal model.
• No silent fallback when timestamps, covariance, or measurements are invalid.

Acceptance metrics should include position error, velocity error, track continuity, ID swaps, false track births, missed tracks, and p50/p95/p99 processing latency.

Phase 2 — Replace straight-line threat logic with bounded prediction

The current  threat.py  relies heavily on constant-velocity time-to-zone and closest-approach calculations. For manoeuvring targets, use a conservative reachable prediction:

• Propagate each plausible motion model.
• Include covariance and a bounded acceleration/turn envelope.
• Assess whether the protected zone is reachable within the warning horizon, not merely whether the current straight-line path intersects it.
• Treat stale tracks and degraded sensors explicitly.
• Produce reasons such as “reachable under maximum turn envelope” or “prediction stale,” rather than implying certainty.
• Keep unknown classification conservative, but avoid allowing a high-speed threat to remain harmless solely because classification confidence is late.

Threat state should be monotonic and explicit:

NEW -> OBSERVE -> WARN -> ALERT -> CRITICAL
                    \-> STALE
                    \-> LOST

De-escalation, cancellation, and stale transitions need separate rules from escalation. Every transition should include the evidence, timestamp, model quality, and uncertainty used.

Phase 3 — Harden the control section

The current  Engine  has a useful human-approval boundary, but it needs a real decision state machine. Each recommendation should have:

• Globally unique recommendation ID.
• Track ID and track-version reference.
• Creation time, expiry time, and source event.
• Threat level and evidence snapshot at creation.
• Required authority/role.
• State:  OPEN ,  APPROVED ,  REJECTED ,  EXPIRED ,  CANCELLED , or  SUPERSEDED .
• Idempotency protection so duplicate approvals cannot create duplicate actions.
• Explicit handling when the track changes, disappears, becomes stale, or is reclassified.
• Operator identity, authentication context, reason code, and free-text note.
• No action on timeout, disconnect, malformed command, or ambiguous state.

The brain should emit recommendations only. Any future effector integration must be a separate, independently authorized subsystem with its own interlocks and safety review—not a hidden extension of  Engine .

Phase 4 — Make timing and failure behavior deterministic

Add system-level controls before live streaming:

• Monotonic timestamps and synchronized wall-clock timestamps for audit.
• Per-stage latency measurements.
• Bounded queues and backpressure.
• Heartbeats and watchdogs.
• Sensor-health and brain-health states.
• Explicit degraded modes for sensor loss, clock faults, overload, and audit failure.
• Fail-closed control behavior: if decision context or authorization is incomplete, do not treat it as approved.
• Resource limits and recovery tests.
• No stale recommendation presented as current.

A live dashboard should show freshness and degraded state prominently, but the brain must enforce those rules independently.

Phase 5 — Strengthen audit and security

The current hash chain detects modification within the in-memory/exported sequence, but it is not sufficient as an operational audit system. Add:

• Authenticated operator identity and role.
• Secure time source and monotonic sequence numbers.
• Recommendation ID and decision correlation.
• Append-only durable storage.
• Keyed signatures or an externally anchored integrity mechanism.
• Key rotation and compromise handling.
• Startup/restart records and audit-gap detection.
• Audit failure as a visible system fault, never a successful export.
• Replay tests proving that decisions, stale states, and track revisions are reproducible.

Do not place credentials, signing keys, or trust decisions in the dashboard or replay file.
