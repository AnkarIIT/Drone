# Skybrain Final Plan

## Mission

Build Skybrain as a resilient, sensor-fused, human-controlled defensive airspace
decision system for detecting, tracking, classifying, and prioritizing drones
under uncertainty.

The system must remain useful under high-speed manoeuvres, sensor dropouts,
clutter, spoofed identity, degraded communications, GPS-denied conditions,
multiple simultaneous tracks, operator overload, restarts, clock errors, and
audit failures.

Skybrain must not autonomously select, authorize, or execute offensive effects.
The brain produces recommendations; authorized external systems and personnel
remain responsible for any response.

## System architecture

    Sensors
      -> timestamp and quality validation
      -> measurement normalization
      -> multi-sensor association
      -> IMM / manoeuvring tracker
      -> identity and track-quality assessment
      -> uncertainty-aware threat prediction
      -> human decision state machine
      -> authenticated audit stream
      -> operator display and approved integrations

The dashboard is secondary. It consumes a versioned brain-output contract and
never performs threat calculations or decision logic.

## Phase 0: Define the operational envelope

Specify measurable limits before further algorithm tuning:

- maximum target speed;
- maximum acceleration, turn rate, climb rate, and jerk;
- sensor update rates and latency;
- timestamp accuracy and clock synchronization;
- detection range and required warning time;
- expected dropout duration;
- number of simultaneous targets;
- minimum track quality for each threat state;
- friendly-aircraft and authorized-drone procedures;
- RF spoofing, GNSS denial, clutter, birds, and urban multipath conditions;
- maximum acceptable end-to-end latency.

“Fast drone” must become a testable envelope. Every gate and coast parameter
depends on this definition.

Deliverable: an operational-envelope document and scenario matrix.

## Phase 1: Build the tracker core

Use an IMM with at least:

1. constant-velocity cruise;
2. acceleration/Singer manoeuvre;
3. coordinated-turn manoeuvre.

Model probabilities are diagnostic evidence only. They must not be presented as
an “evasive attacker” conclusion.

Required tracker behavior:

- Mahalanobis gating adapted to speed, uncertainty, and scan interval;
- association cost combining position likelihood, velocity consistency, track
  age, quality, sensor/signature evidence, and authenticated identity evidence;
- stable IDs through crossings and short dropouts;
- track confirmation based on time, quality, and evidence;
- adaptive coast time based on uncertainty growth and target dynamics;
- explicit NEW, CONFIRMED, DEGRADED, STALE, and LOST states;
- an explicit out-of-sequence measurement policy;
- rejection and audit of invalid timestamps, covariance, and measurements;
- positive-semidefinite covariance checks;
- no silent fallback after numerical or sensor faults;
- sensor contributors and freshness metadata on every track.

Track diagnostics should include position and velocity uncertainty, acceleration
estimate, last update time, missed scans, identity evidence, model
probabilities, track quality, association confidence, and data age.

Deliverable: IMM tracker with deterministic diagnostics and unit tests.

## Phase 2: Harden identity and classification

Identity must be evidence-based and fail closed.

Rules:

- authenticated friendly identity is strong positive evidence, not an absolute
  override;
- unverified broadcast IDs are never trusted alone;
- RF, radar, EO/IR, acoustic, and kinematic evidence must be correlatable;
- identity conflicts create an explicit IDENTITY_CONFLICT state;
- impossible motion and identity changes are audited;
- a friendly claim cannot automatically suppress a physically dangerous track;
- classification confidence remains separate from threat severity.

Use labels such as:

    FRIENDLY_CONFIRMED
    DRONE_LIKELY
    BIRD_LIKELY
    UNKNOWN
    IDENTITY_CONFLICT
    UNRESOLVED

Deliverable: classifier contract, spoofing tests, crossing-track tests, and
identity-conflict scenarios.

## Phase 3: Replace straight-line threat assessment

Straight-line time-to-zone logic is insufficient for sharp turns. Implement
uncertainty- and manoeuvre-bounded prediction:

- propagate all plausible motion models;
- include covariance growth;
- include sensor latency and data age;
- include bounded acceleration and turn-rate envelopes;
- compute reachable protected-zone entry intervals;
- distinguish current path from reachable path;
- downgrade confidence when prediction is stale or models diverge;
- prevent false certainty from a single projected line.

Threat output should include current state, reachable entry interval, best
estimate, worst credible estimate, prediction confidence, data freshness,
sensor count, identity confidence, and reason codes.

Example:

    ALERT - reachable critical-zone entry 38-54 s; last update 0.8 s ago;
    two corroborating sensors; identity conflict unresolved.

Threat states:

    NEW
    OBSERVE
    WARN
    ALERT
    CRITICAL
    STALE
    LOST
    RESOLVED

Escalation and de-escalation must be separate policies. A threat must not
instantly disappear because one scan becomes benign.

Deliverable: bounded threat predictor with adversarial manoeuvre tests.

## Phase 4: Make the control layer deterministic

Every recommendation must be a formal, traceable object containing:

- globally unique recommendation ID;
- track ID and track-version ID;
- creation time;
- expiry time;
- threat state;
- immutable evidence snapshot;
- identity and sensor evidence;
- required authority or role;
- reason codes;
- current recommendation state.

Recommendation states:

    OPEN
    APPROVED
    REJECTED
    EXPIRED
    CANCELLED
    SUPERSEDED

Rules:

- decisions are single-use and idempotent;
- duplicate decisions are rejected and audited;
- mismatched track versions are rejected;
- expired recommendations cannot be approved;
- silence never means approval;
- network loss never means approval;
- stale evidence cannot silently remain actionable;
- disappearing or reclassified tracks update the recommendation;
- every transition records who, when, why, and which evidence snapshot was used;
- the brain never directly activates an effector.

Deliverable: deterministic control state machine and decision-transition tests.

## Phase 5: Design for saturation and operator workload

Prioritize attention using:

1. reachable protected-zone entry time;
2. uncertainty-adjusted threat;
3. identity conflict;
4. track freshness;
5. proximity and consequence;
6. sensor corroboration;
7. recommendation age.

Merge duplicate sensor reports, avoid repeated alerts for unchanged evidence,
show the most urgent unresolved decision first, and preserve access to the full
evidence chain.

The operator must be able to distinguish estimate, prediction, confidence,
confirmation, freshness, and authority state immediately. Acknowledgement must
not imply approval.

Deliverable: human-factors review, alert-saturation tests, and operator
usability evaluation.

## Phase 6: Resilience and degraded modes

Treat these as normal operating states:

- GPS unavailable;
- clock disagreement;
- sensor dropout;
- network loss;
- queue overload;
- audit failure;
- process restart;
- model divergence;
- conflicting identity;
- stale track;
- partial sensor availability.

Each mode requires deterministic behavior, visible health status, a clear
operator message, bounded recovery behavior, an audit record, and test
coverage.

The system must fail closed for authorization and control while preserving
detection and evidence collection where safe.

Deliverable: fault-injection suite and recovery requirements.

## Phase 7: Secure, durable audit

The current hash chain is useful integrity evidence but is not a complete
operational audit system. Add:

- authenticated operator identity;
- role and authority;
- secure wall-clock timestamp;
- monotonic sequence;
- recommendation correlation;
- track-version correlation;
- append-only durable storage;
- startup, shutdown, restart, and recovery records;
- key management and rotation;
- external integrity anchoring where appropriate;
- audit-gap detection;
- audit failure as a visible system fault;
- deterministic replay of decisions and state transitions.

Credentials and signing keys must never enter the dashboard or replay payload.

Deliverable: durable audit subsystem, tamper tests, restart tests, and replay
verification.

## Phase 8: Live stream after the brain contract is stable

The live interface may stream brain state, track updates, event updates,
recommendation updates, health/degraded-mode updates, and audit acknowledgements.

It must support:

- sequence numbers;
- reconnect and resume;
- duplicate suppression;
- stale-data detection;
- backpressure;
- bounded queues;
- authentication and authorization;
- explicit connection health;
- server-side decision validation.

The dashboard must never approve a stale or superseded recommendation merely
because it was displayed earlier.

Deliverable: versioned live API and disconnected/reconnect tests.

## Verification program

### Scenario replay

Include fast straight targets, weaving targets, late sharp turns, coordinated
turns, crossing drone and bird tracks, spoofed friendly IDs, identity changes,
sensor dropouts, delayed measurements, GPS-denied operation, clutter bursts,
multiple simultaneous targets, and saturated recommendation queues.

### Monte Carlo

Measure position error, velocity error, track continuity, ID swaps, false track
births, missed tracks, false warnings, missed warnings, warning lead time,
p50/p95/p99 latency, CPU behavior, and memory behavior.

### Fault injection

Test invalid timestamps, clock rollback, covariance failure, sensor silence,
duplicate measurements, network disconnection, brain restart, audit storage
failure, duplicate operator commands, expired recommendations, and superseded
recommendations.

### Higher-fidelity validation

Before operational consideration, conduct hardware-in-the-loop tests,
representative sensor replay, shadow-mode trials, independent safety review,
independent cybersecurity review, human-factors evaluation, red-team spoofing
tests, overload exercises, and reproducible release/rollback procedures.

Simulator success is necessary but not sufficient evidence.

## Release gates

No live operational integration until all gates pass:

| Gate | Required result |
|---|---|
| Fast-target tracking | Performance within the defined speed and manoeuvre envelope |
| Track identity | No unacceptable swaps during crossings, dropouts, or spoofing |
| Threat prediction | Conservative bounded prediction with explicit uncertainty |
| Warning timing | Worst-case latency and warning lead time measured |
| False alarms | Measured across birds, clutter, friendly traffic, and benign drones |
| Control safety | No duplicate, stale, unauthorized, or ambiguous approvals |
| Resilience | Safe behavior under sensor, clock, network, process, and audit faults |
| Audit | Complete attributable and tamper-evident decision history |
| Human factors | Operators understand freshness, uncertainty, identity, and authority |
| Security | Authentication, authorization, threat modeling, dependency review, and red-team testing |
| Deployment | Reproducible builds, monitoring, rollback, and incident procedures |

## Immediate implementation order

1. Reconcile the repository with the claimed IMM implementation.
2. Define the maximum target and sensor envelope.
3. Add tracker diagnostics and scenario fixtures.
4. Harden association, lifecycle, uncertainty, and freshness.
5. Implement bounded manoeuvre-aware threat prediction.
6. Finish the recommendation state machine with track versions and stale
   cancellation.
7. Add failure states, health monitoring, and fault injection.
8. Upgrade the audit system for authenticated durable operation.
9. Define and test the versioned live-stream contract.
10. Connect the dashboard in read-only shadow mode.
11. Conduct hardware-in-the-loop and operator evaluation.
12. Release only after independent safety and security approval.

## Final principle

Skybrain should not try to be an autonomous warrior. It should remain accurate,
explainable, resilient, conservative, and accountable when the environment is
confusing and time is short. That is the extraordinary capability worth
building.
